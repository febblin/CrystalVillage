# CrystalVillage — Тяжёлый 3D-прогон для jdJavaSE

<img width="956" height="593" alt="image" src="https://github.com/user-attachments/assets/036ee048-6fa0-4be8-8f42-4026e894ed59" />


Этот тест представляет собой **первую серьёзную 3D-нагрузку** для jdJavaSE. Демонстрация создана, чтобы проверить пределы возможностей кастомной JVM на реальном железе Sony PSP при работе с API LWJGL 2.0.

В отличие от простых тестов (вроде отрисовки одного куба или загрузки текстур), `CrystalVillage` симулирует сцену, близкую к реальной инди-игре: статичное окружение с запечённым светом и множество динамических объектов с независимой анимацией.

## 🏗️ Состав сцены
*   **Статическое окружение:** 48 домов (основания — кубы с триангуляцией, крыши — пирамиды), объединённых в один общий VBO. Земля — сетка 20×20.
*   **Динамические объекты:** 200 вращающихся октаэдров (кристаллов) с разными скоростями вращения по трём осям.
*   **Освещение:** Полностью запечённое (Baked Lighting). Цвет каждой вершины рассчитывается математически на стороне Java при загрузке карты, исходя из нормали грани и направления света из `level2.json`. Это позволяет не тратить ресурсы на расчёт света в реальном времени.
*   **Управление:** Свободная камера от первого лица (WASD + мышь/аналоговый стик).

## 📊 Технические показатели (на реальной PSP 3008)
*   **Количество треугольников на кадр:** ~4 992 
    *   Земля: 800
    *   Дома: 2 592
    *   Кристаллы: 1 600
*   **Draw Calls на кадр:** 201 (1 для уровня + 200 для кристаллов).
*   **FPS:** стабильные **30 FPS**.
*   **Загрузка CPU:** **~87%**.
*   **Загрузка GE (GPU):** минимальная (графический чип не является узким местом).

## 🏆 Достижения
1.  **Архитектура VBO подтверждена.** Статическая геометрия (дома и земля) загружается в видеопамять один раз и рисуется одним вызовом `glDrawArrays`.
2.  **Запечённый свет работает.** Визуально дома и земля выглядят объёмно, несмотря на отсутствие `GL_LIGHTING`. 
3.  **Динамика в реальном времени.** Стек матриц (`glPushMatrix` / `glPopMatrix`) успешно справляется с вращением 200 независимых объектов.
4.  **Стабильность JVM.** Кастомный интерпретатор без сбоев обрабатывает десятки тысяч операций с плавающей точкой и нативные вызовы каждую секунду.

## ⚠️ Узкие места (почему не 60 FPS?)
Текущая просадка с 60 до 30 FPS — это **точно не вина PSP**. GE (Graphics Engine) способен переваривать десятки тысяч треугольников в кадре без просадок. 

Проблема кроется в **накладных расходах интерпретатора JVM**:
1.  **1200 матричных операций в кадр.** Для отрисовки 200 кристаллов игра делает 200 `glPushMatrix`, 200 `glTranslatef`, 600 `glRotatef` и 200 `glPopMatrix`. Каждый этот вызов — это переход из Java в C через интерпретатор и последующая математика умножения матриц 4×4 внутри `sceGum`. Это съедает почти весь бюджет процессора.
2.  **201 Draw Call.** Отправка 200 отдельных команд отрисовки для кристаллов вместо одной пакетной.
3.  **Накладные расходы нативной передачи.** Каждый вызов `glDrawArrays` и матричных функций требует синхронизации стека операндов JVM и подготовки параметров.

## 🚀 Планы по оптимизации (Dynamic VBO)
Для достижения стабильных **60 FPS** при 200+ динамических объектах планируется переход на **Dynamic VBO (CPU-батчинг)**:
*   Матричная математика и трансформация вершин кристаллов будут перенесены на сторону Java (с использованием обычных массивов `float[]` для минимизации нагрузки на Garbage Collector).
*   Каждый кадр готовые мировые координаты всех 200 кристаллов будут собираться в один общий `FloatBuffer`.
*   Вместо 200 draw call'ов и 1200 матричных вызовов GE получит **один** вызов `glBufferData` и **один** вызов `glDrawArrays`.
*   Ожидаемый результат: падение загрузки CPU до **~20–25%** и возврат к стабильным **60 FPS**.

## 🛠️ Запуск
1.  Распакуйте в PSP\GAME\
2.  Запустите через лаунчер jdJavaSE.
